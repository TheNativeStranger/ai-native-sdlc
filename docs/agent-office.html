Agent Office

Agent office

The six stages of the playbook, drawn as the office of a one-person company. Each room is a stage. Agents sit at desks, skills stand on shelves, hooks wait at the doors. The human sits above the loop, on the decision floor.

Planning draft · 11 November 2026 · Based on The AI-native SDLC playbook by Louis Claxton, Anthropic. This page is an independent adaptation and is not published or endorsed by Anthropic. Running the seven roles as agents is this draft's interpretation: the playbook assigns those roles to people, and mentions a reviewing agent only as a confidence gate in the headless loop.

The source it follows: The AI-native SDLC playbook

This plugin does not invent a method; it installs a published one. The source is The AI-native SDLC playbook, in which Anthropic's Applied AI team collects the practices it uses with customers. It is not a formal standard; it is Anthropic's own published guide to running the software lifecycle with Claude Code.

  • A known sourceThe six stages, the artifact chain and the gates come from the playbook; the table below shows which play each part rests on.
  • Ready to useThe playbook describes the method and shows short samples; it does not ship an installable package. This plugin provides one.
  • Fitted to one personThe playbook is written for large organizations. Approval seats let the same setup run in a one-person company.

The plugin's own sample files

The playbook shows a few-line sample for each play. The files below are not copies of those; they are the templates this plugin will ship, with section headings that follow the structure the playbook proposes. For the original samples, read the playbook.

intent/order-tracking/intent.md

# Intent: order tracking
Author: A. Yilmaz (customer support). Status: draft.

## Problem
Customers call the support line to find out where their order is.
The support team spends most of its day on these questions.

## Proposed outcome
A customer sees the order status, the next step and the estimated
delivery day in their account.

## Affected users and systems
Customers, the support team, the order service, the carrier integration.

## Constraints
No new personal data is collected. Existing sign-in only.

## Open questions
Can people who ordered as guests track their order too?

CLAUDE.md

# Order service

## Commands
- Build: make build
- Test: make test (unit), make itest (integration, needs docker)
- Lint: make lint (also runs in CI; fix before pushing)

## Conventions
- Money amounts are always integers in minor units.
- Every endpoint has an integration test.
- Dates are stored in UTC and converted only in the interface.

## Architecture
- api/ receives requests, core/ holds business rules,
  adapters/ talks to outside systems.
- Event schemas live in schemas/; generated files are never hand-edited.

## Verifying your work
Run all three commands and show the output. If a test fails, fix the
code, not the test.

## Things Claude gets wrong
- Do not bump dependency versions; that is opened as its own task.
- The legacy/ package is frozen; changes go under current/.

# Secure API

When you add or change an endpoint:
1. Authentication: no anonymous route outside /health.
2. Input validation: validate the body against the schema and reject
   unknown fields.
3. Audit trail: every state-changing call records who, what, which
   record and when.
4. Data class: a field marked as personal data in the schema never
   reaches a log or an error message.

Decision floor · above the loop

You

  • You own all seven approval seats
  • You hold a seat yourself or leave it to its role agent
  • Production release authority always stays with you

The intake room. An idea is written in its owner's words and enters the repo.

Output intent.md
Gate · product owner seatWhoever holds the seat accepts the intent. Default: human.

The design room. Requirements and design are written in one session.

Output spec.md
Gate · product owner and policy owner seatsThe product owner accepts the spec. The policy owner steps in only when a conflict is flagged.

The workshop. No code is written without an accepted plan.

Output plan.md, then code

The test bench. Every session checks its own work before a person sees it.

Order rule: one finishes before the next starts

Each room ends with a document and the next room starts by reading it. The next door does not open until that document is accepted. Three layers hold the rule; if one is skipped, another catches it.

LayerWhere it runsWhat it does
Stage lock (hook)Inside the agent, before every file writeLooks at which room the file belongs to. If the previous room's document is not accepted, it blocks the write and says why
Stage check (CI)On every PRA PR that brings spec.md needs an accepted intent.md; a PR that brings code needs an accepted spec.md and plan.md. Otherwise the merge is stopped
Branch protectionOn GitHubOnly approved PRs reach the main branch. "Accepted" means the document is on main
TransitionWhat opens itWhere it returns if it stays shut
Plan → Designintent.md merges to mainBack to the originator with questions
Design → Buildspec.md merges to mainTo the design agent; to Plan if the intent is incomplete
Inside Buildplan.md is acceptedThe plan is revised; to Design if the spec is incomplete
Build → TestThe coding agent reports doneStays with the coding agent until tests pass
Test → DeployTests and evals pass, a PR opensTo the coding agent
Deploy → productionThe code owner merges, the release manager authorizesTo Build; to Design if the spec was wrong
Maintain → PlanA band is breached or a new item arrivesEvery new item enters the chain at Plan

Approval seats

Each of the seven roles has an approval seat. Who sits in it comes from one config file. One person can hold all seven; as the team grows, seats are handed over and the setup stays the same.

SeatWhat it approvesDefault setting
Product ownerAcceptance of the intent and the specHuman
Policy ownerSecurity and compliance conflicts flagged in the spec or the PRHuman only when flagged
Tech leadThe plan; the spec for higher-risk workHuman only when flagged
Platform engineerChanges to the rules file, skills and hooks; eval resultsHuman only when flagged
Code ownerMerging a PR to mainHuman
Release managerProduction releaseHuman; cannot be changed
Service ownerA monitoring finding: fix now, schedule or dismissHuman only when flagged
SettingWhat happens
HumanThe role agent does the first pass and writes its findings; the named person approves
Human only when flaggedThe role agent passes the work if it finds nothing, and escalates to the person if it does
AgentThe role agent approves
  • The author cannot approve. The agent that produced a piece of work cannot sit in the seat that approves it. This is not configurable.
  • Production release is always human. The release manager seat cannot be set to "agent".
  • A check stands behind every role agent. An agent's approval is advisory; what enforces the rule is the hook, the CI check and branch protection.

Room files

Everything each room needs: who works there, which files are set up, how the gate is held, how the work runs, and how it is measured.

1

Plan

Purpose
An idea is written once, in its owner's words, and becomes a document the next room can read.
Input
A person's idea, a filed ticket, or a finding from the Maintain room
Output
intent/<name>/intent.md
Prerequisite
None. The chain can start here.

Roster and files

PartTypeJobFile
Product owner agentRole agentAsks what an analyst would ask: scope, users, constraints, what success looks like. Checks the document against the template.claude/agents/product-owner.md
Intent templateSkillDefines the document's five sections.claude/skills/intent-template/SKILL.md
/intentCommandStarts the conversation and writes the document at the end.claude/commands/intent.md
GitHubConnectorCommits the document as a PR on behalf of an originator who does not use gitAccount setting

Sections of the document

Problem · Proposed outcome · Affected users and systems · Constraints · Open questions. The heading carries the author and the status.

Gate

Product owner seat · default humanCondition: all five sections are filled and the originator has corrected any misunderstanding.Enforced by: branch protection; the document reaches main only through an approved PR.If it fails: back to the originator with questions.

How the work runs

  1. The originator describes the problem in their own words; no formal language is needed.
  2. The product owner agent asks questions until the idea is concrete.
  3. The agent writes the result as intent.md from the template.
  4. The originator corrects anything that was misunderstood.
  5. The document opens as a PR; the seat accepts or rejects it.

Measurement

Leading
Time from first conversation to a committed document
Lagging
Share of intents accepted; number of changes to the intent after the spec is written

Design

Purpose
Requirements and design are written in one session. Policy is applied while the spec is written rather than found in a review weeks later.
Input
An accepted intent.md
Output
intent/<name>/spec.md, next to the intent
Prerequisite
The Plan room and the policy skills

Roster and files

PartTypeJobFile
Design agentWorking agentWrites the requirements and design spec from the intent; states clearly where it cannot satisfy conflicting policies.claude/agents/designer.md
Product owner agentRole agentChecks that the spec solves the stated problem and that the intent's open questions are answered or carried forward.claude/agents/product-owner.md
Policy owner agentRole agentLists the flagged conflicts so each can be resolved with the owner of that policy.claude/agents/policy-owner.md
Security, compliance, brand and UXSkillThe policies the spec has to follow.claude/skills/security/, compliance/, brand-ux/

Sections of the document

Requirements · Design · Flagged concerns · Open questions carried from the intent. For interface work a mock is prepared separately and linked from the spec.

Gate

Product owner seat · default humanCondition: the spec meets the intent and every flagged concern is resolved.The policy owner seat steps in only when a concern is flagged; the tech lead seat only for higher-risk work.Enforced by: branch protection and the stage check. Accepting the spec is what starts plan mode in the Build room.If it fails: back to the design agent; to the Plan room if the intent is incomplete.

How the work runs

  1. At first /spec is run by hand; once the routine holds, the job starts by itself when the intent merges.
  2. The design agent writes the spec with the skills loaded.
  3. Flagged concerns are worked through first; they are the points an analyst would have escalated.
  4. The spec is committed next to the intent. The pair records what was asked for and what was decided.
  5. The seat decides whether the spec moves on to Build.

Measurement

Leading
Time between the intent commit and the spec commit
Lagging
Number of changes to the spec after the plan is written

Build

Purpose
Nothing is implemented without an accepted plan. Institutional knowledge becomes files the agent reads; guardrails run as code rather than as habits.
Input
An accepted spec.md and intent.md
Output
intent/<name>/plan.md, then code and tests
Prerequisite
The rules file. Plan mode and hooks can be set up with nothing first.

Sections of the document

Files that change · Order of work · Risks · Proof (which test, which screenshot). The bar: an engineer who never saw the conversation could implement from the plan alone.

Gate

Tech lead seat · default human only when flaggedCondition: the plan names the files, the order and the tests that prove it.Enforced by: plan mode, which blocks file edits before acceptance; the stage check, which looks for plan.md in any PR that brings code.If it fails: the plan is revised; back to the Design room if the spec is incomplete.

How the work runs

  1. The coding agent starts in plan mode with the intent and the spec.
  2. It writes a plan naming the files that change, the order of work and the tests that prove it.
  3. The tech lead agent interrogates the plan; it is revised until it is clear enough.
  4. The accepted plan is committed as plan.md.
  5. The coding agent implements. If the work departs from the plan, the plan is updated in the same commit.
  6. Work that touches different files runs in parallel worktrees; work that shares files runs in one session, one after another.
  7. When the agent makes the same mistake twice, the correction goes into the rules file.

Measurement

Leading
Share of changes that merge from the first implementation pass; time from plan acceptance to merge
Lagging
Rework cycles per change; how often the merged diff still matches the plan
4

Test

Purpose
Every session checks its own work before a person sees it. The configuration that steers the agent is regression-tested like the code it writes.
Input
Code and the proof items in plan.md
Output
Test output, build log, eval results
Prerequisite
The feedback loop needs nothing first. The eval suite needs the rules file and the loop.

Roster and files

PartTypeJobFile
Feedback loopScriptOne command each for test, build and lint; exits non-zero on failureMakefile or package.json
Verification blockDocumentLists the commands with an example of healthy output; the rule to run them and show the output before reporting doneCLAUDE.md
VerifierSubagentIn a fresh context, runs the app and exercises the changed behavior and its two nearest flows; reports only, fixes nothing.claude/agents/verifier.md
Test-file lockHookStops the agent editing test files during a fix task.claude/hooks/test-lock.sh
Eval suiteCI jobTwenty to fifty real tasks. Runs nightly and whenever the rules file, a skill or a hook changesevals/*.json, evals/check.sh, .github/workflows/agent-evals.yml
Platform engineer agentRole agentInvestigates a drop in the eval pass rate; maintains the hooks and the loop.claude/agents/platform-engineer.md

Gate

Automatic · platform engineer seat, human only when flaggedCondition: tests, build and lint pass; the eval pass rate has not fallen below the threshold.Enforced by: a CI merge check.If it fails: back to the coding agent. If a configuration change lowered the pass rate, that change does not merge.

How the work runs

  1. The target is written so it can be checked: "these tests pass", "the screenshot matches the mock".
  2. For a bug fix, the failing test is written and committed first; the agent then fixes the code without editing the test.
  3. For interface work the agent implements, takes a screenshot, compares it with the mock and adjusts.
  4. Before reporting done, the agent runs the three commands and shows the output.
  5. The verifier does the final check in a fresh context.
  6. Every production incident is added to the suite as a permanent eval.

Measurement

Leading
First-pass CI success rate for agent-written changes; the eval pass rate over time
Lagging
Review time per PR; regressions caught in CI against those found in production

The rules file. The CI/CD pipeline needs PR review and the production gate.

Environment tiers

In development the agent deploys freely. Staging sits in between. In production the agent only prepares the release; the release manager seat authorizes it.

Gate

Code owner seat · default humanCondition: findings are addressed; the change does what the plan intended and the risk is acceptable.Enforced by: branch protection. Findings do not approve or block on their own.If it fails: back to the Build room; to the Design room if the spec was wrong.
Release manager seat · human, cannot be changedCondition: the checklist is complete and the rollback was rehearsed in staging.Enforced by: the production gate hook.If it fails: the release waits; an unhealthy release is rolled back with one command.

How the work runs

  1. When a PR opens, the review job runs and writes findings ranked by severity.
  2. When the agent is tagged on a comment, it makes the fix and pushes it; request and change stay on record in the PR.
  3. When review flags the same mistake a second time, the correction goes into the rules file.
  4. The seat merges; the merged PR triggers the pipeline.
  5. The agent prepares the release; production opens on authorization.
  6. Once a month the findings are rated and the nit cap and excluded paths are tuned.

Measurement

Leading
Time to first review; share of comments resolved without a person touching the branch; time spent waiting at each gate
Lagging
Defects caught before merge against those escaping to production; deployment frequency, change failure rate and time to restore
6

Maintain

Purpose
The loop closes. A trigger invokes the agent with no person in the path, and what it finds re-enters the chain as a new intent.
Input
Production metrics, tickets, scheduled checks
Output
An incident record and a new intent.md
Prerequisite
The Plan room, PR review, hooks and a rehearsed rollback

Roster and files

PartTypeJobFile
Detection scriptScriptComputes the rolling mean and deviation of one metric and catches slow drift as well as spikes. No model inside; it has unit testsops/detect.py
Band configDocumentThree tiers: at the first band only log, at the second the agent diagnoses read-only, at the third it may open a PR or trigger a pre-approved rollbackops/bands.yaml
Monitoring jobCI jobRuns the script on a schedule and invokes the agent headless when a band is breached.github/workflows/monitor.yml
Service owner agentRole agentWrites the diagnosis in intent form: the anomaly and its evidence, a proposed outcome, affected systems, open questions. Triages the queue.claude/agents/service-owner.md

Gate

Automatic · service owner seat, human only when flaggedCondition: the tier sets what the agent may do; the agent touches production only through gated routes.Enforced by: version-controlled band config and permissions. In the headless chain an independent confidence gate stands between rooms: either a deterministic check or a role agent.The seat decides for each finding: fix now, schedule or dismiss. Dismissals tune the bands.

How the work runs

  1. One metric with a stable baseline is chosen: CI test failure rate, post-deploy error rate or PR cycle time.
  2. The script watches the metric and acts by tier when a band is breached.
  3. The service owner agent writes the diagnosis as intent.md; the finding enters the chain at the Plan room.
  4. A small, well-bounded fix arrives directly as a PR at the review gate.
  5. When the fix ships, an eval is added for the incident.

Measurement

Leading
Time from band breach to an intent in the queue
Lagging
Share of findings that become merged fixes; repeat incidents of the same class

Setup order

The order of the rooms is not the order of setup. Following the playbook's dependency graph, five parts can be set up with nothing first and the rest build on them. Each step is run by hand at first; the self-running loop is the last stage.

OrderWhat is set upWhat it depends on
1Rules file, plan mode, feedback loop, hooks, intent captureNothing; all five are entry points
2Skills, subagentsRules file
3Requirements and designIntent capture, skills
4Eval suiteRules file, feedback loop
5PR reviewRules file; skills help
6CI/CD pipelinePR review, hooks
7Closing the loopIntent capture, PR review, hooks, CI/CD pipeline

Three things cannot be set up from files alone: branch protection is turned on in GitHub settings, the API key for CI is added to the repo secrets, and an end-to-end run on a real PR needs a session with write access.
